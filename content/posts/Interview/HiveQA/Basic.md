### 分桶为什么能加速查询？

> “分桶通过哈希函数将相同键值的行分配到同一个物理文件（桶）中。这种物理聚合带来了两大核心优势：
> 
> 1. **对于JOIN操作**：当两个表在相同的JOIN键上分桶且桶数匹配时，Hive可以执行**桶映射连接（SMB Join）**。相同键值的数据必然在相同编号的桶中，因此可以在Map端直接进行本地JOIN，完全避免了Shuffle的网络传输开销，这是数量级的性能提升。
> 
> 2. **对于采样和过滤**：由于数据已按哈希值均匀分布，采样操作可以直接读取整个桶文件，而无需扫描全表。如果查询条件包含分桶列的等值过滤，也可以只读取相关桶，实现桶级别的裁剪。
> 
> 不过，分桶也有代价，主要是写入时的额外计算开销，以及桶数设置不当可能产生小文件问题。实际生产中，我们通常**先按时间分区，再在高基数的JOIN键上分桶**，桶数根据数据量控制在使每个桶200MB-1GB大小为宜。”

### 分桶时如果桶数不匹配会发生什么？

#### A分桶+B不分

“如果只有A表对JOIN键分桶而B表没有，那么Hive无法使用**桶映射连接（Bucket Map Join）**​ 这一最高效的优化。具体执行路径取决于B表的大小：

1. **如果B表是小表**：Hive会使用普通的Map Join（广播连接），将B表广播到所有Mapper，与A表的每个桶在Map端进行JOIN。此时A表的分桶优势有限，只是实现了并行读取。

2. **如果B表也是大表**：Hive会退回到普通的Reduce Side Join（Shuffle Join）。虽然A表的数据在存储时已经按JOIN键哈希分布，但B表没有，所以仍然需要完整的Shuffle过程，分桶的优化效果大打折扣。

**最佳实践**是确保需要频繁JOIN的两个大表都在JOIN键上分桶，且桶数设置为相同或成倍数。在生产环境中，我们通常会在数据仓库的维度表和事实表上都采用这种设计，特别是对于用户行为分析这类JOIN密集的场景。”

#### A分64桶+B分32桶

"当两表在JOIN键上都分桶但桶数不同时，效率取决于桶数关系：

1. **如果桶数相同**：可以触发最高效的Bucket Map Join，每个Mapper只读取对应编号的桶文件，在内存中完成JOIN，完全避免Shuffle。

2. **如果桶数成倍数**（如64桶和32桶）：Hive仍可优化。通过将桶数多的表的多个桶映射到桶数少的表的一个桶，在Mapper端进行本地JOIN。虽然每个Mapper处理的数据量略有增加，但仍避免了Shuffle，效率接近桶数相同的情况。

3. **如果只有一边分桶**：分桶的优势有限。如果未分桶的表小，可触发Map Join但需广播；如果未分桶的表大，则退回到Reduce Join，分桶只能略微优化Map端读取。

4. **如果桶数互质**：难以优化，通常退回到普通JOIN。

生产中最佳实践是：确保频繁JOIN的大表在JOIN键上分桶，且桶数相同或成倍数，并配合ORC/Parquet格式以获得最佳性能。"

### 分桶是否还需要Reduce

"在分桶JOIN中不需要Reduce阶段，核心原因是**数据分组工作已经前置到存储阶段完成**。

1. **分桶的本质**：通过对JOIN键哈希，将相同键值的记录**物理上存储到同一个文件**（桶）中。

2. **执行时**：每个Map任务只处理编号相同的桶对。因为相同JOIN键的记录必然在相同编号的桶中，所以**每个Map任务已经持有了完整的JOIN分组**，可以在本地完成全部JOIN操作。

3. **内存使用**：如果小表的桶可装入内存，会使用HashMap方式；如果都是大表，可使用Sort Merge方式流式处理，内存消耗很小。

4. **输出结果**：不同Map任务处理不同桶，输出互不重叠的结果分区，直接就是最终结果，无需合并。

5. **对比普通JOIN**：普通JOIN需要Reduce阶段来收集和分组分散的数据，而分桶JOIN通过预分组消除了这个需求，这是**用存储换计算**的经典优化。

实际生产中，我们通常结合分区和分桶：先按时间分区快速裁剪，再在分区内分桶优化JOIN，配合ORC/Parquet列式存储，实现极致性能。"

## 思考题

如果orders表有1000万行，users表有100万行，都按`user_id`分100个桶：

1. 平均每个Map任务要处理多少行数据？

2. 如果只有10%的user_id有订单，会发生什么？

3. 如果某个user_id有100万行订单（数据倾斜），会怎样？

**答案提示**：

1. orders每个桶≈10万行，users每个桶≈1万行

2. 大部分Map任务的JOIN结果为空，但任务仍需执行

3. 该user_id所在的那个Map任务负载很重，可能出现长尾任务

这就是分桶优化的局限之一：无法解决桶内数据倾斜问题。

### Q1：为什么TABLESAMPLE与WHERE联用会得到意外结果？

**A**：因为TABLESAMPLE在查询计划中优先于WHERE执行。它会先随机选取物理数据块，然后在这些块中应用WHERE过滤。如果目标数据恰好不在选取的块中，结果可能为空。

### Q2：如何在保证随机性的同时提高抽样性能？

**A**：推荐方案：

1. 对热数据使用**分桶表+分桶抽样**

2. 对历史数据使用**分区剪枝+RAND()抽样**

3. 创建**物化视图**存储常用抽样结果

### Q3：如何评估抽样数据的代表性？

**A**：抽样后应验证：

```sql
-- 对比关键指标
WITH sample_stats AS (
  SELECT AVG(amount) as avg_amt, COUNT(DISTINCT user) as users
  FROM orders TABLESAMPLE(1 PERCENT)
),
full_stats AS (
  SELECT AVG(amount) as avg_amt, COUNT(DISTINCT user) as users
  FROM orders
)
SELECT 
  ABS(s.avg_amt - f.avg_amt) / f.avg_amt as amt_error_rate,
  ABS(s.users - f.users) * 1.0 / f.users as user_error_rate
FROM sample_stats s CROSS JOIN full_stats f;
```

- **ORC vs Parquet如何选择？**
  
  > "在纯Hive环境中，优先选择ORC，因为针对Hive优化更好，支持ACID事务。在多引擎环境（特别是Spark）中，选择Parquet，因为生态支持更广。如果数据结构复杂、嵌套层次深，Parquet的Dremel算法更有优势。"

- **列存储为什么查询快？**
  
  > "列存储在OLAP场景快是因为：1) 查询只需读取相关列，减少I/O；2) 同列数据类型一致，压缩率高；3) 便于向量化计算和谓词下推。但牺牲了单行读写性能。"

- **ORC的索引机制如何工作？**
  
  > "ORC在每个Stripe（默认1万行）中为每列维护轻量级索引，包含min、max、count。查询时先检查索引，如果查询条件不在[min,max]范围内，则跳过整个Stripe，这叫谓词下推。"

- **如何解决小文件问题？**
  
  > "1) 使用`ALTER TABLE CONCATENATE`合并小文件；2) 调整写入任务的并行度；3) 使用`distribute by`控制Reduce输出；4) 定期执行Compaction作业。"
